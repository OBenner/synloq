## 1. Модель угроз

**Активы:** bearer-токены ролей и оператора (`<synloqHome>/credentials/`), содержимое сообщений в SQLite, целостность состояния доставки, доступность relay.

**Граница доверия:** loopback-HTTP `127.0.0.1:4100` без TLS. Это корректный выбор для local-first, но важно зафиксировать, что именно это значит:

1. **Любой локальный процесс** (любого пользователя на машине) может открыть TCP-соединение к relay. Без валидного токена он получает 401 — перебор 256-битных токенов непрактичен, лимита на попытки аутентификации нет (и не критично при такой энтропии).
2. **Кто угодно на машине может занять порт 4100 раньше relay** (непривилегированный порт). Это главная практическая угроза — см. H1.
3. **Процесс с правами текущего пользователя** может прочитать token-файлы напрямую (0600 не защищает от самого пользователя) и переписать `credentials.json`, добавив свой хэш. Это фундаментальное свойство local-first, а не дефект, но оно должно быть явно записано в модели угроз: компрометация любого процесса пользователя = компрометация всех ролей проекта.
4. **Агенты-участники доверенные, но не всесильные:** роль с валидным токеном может слать сообщения любому участнику, читать только свой inbox, ack только свои сообщения. Операторский токен = полный контроль (pause/resume/replace-session/doctor/send от `operator`). Кража operator-токена — наихудший сценарий уровня проекта.

**Вне модели (явно out of scope, совпадает с README/protocol §9):** сетевая атака извне (loopback-only), шифрование трафика, недоверенные операторы, prompt injection между агентами (relay — транспорт, не фильтр содержимого).

## 2. Что уже сделано правильно (подтверждено кодом)

- **Loopback-only гарантия тройная:** `RelayHttpServer.listen()` отклоняет не-loopback host; supervisor `endpoint()` принимает только `http://127.0.0.1` / `http://[::1]` без userinfo/query/path; adapter-конфиги валидируются `loopbackHttp` refine. Fail-closed во всех трёх местах.
- **Нет спуфинга отправителя:** `from` подставляется из аутентифицированной identity (`relay-service.ts:49`), клиентский ввод по `from`/`project` отбрасывается схемой.
- **Авторизация по получателю:** inbox, ack, reply-parent, delivery receipt/failure — везде проверка `to === identity.agentId`; чужой inbox недоступен (кроме operator — осознанно).
- **Токены:** 32 байта `randomBytes`, at rest — SHA-256, сравнение через `timingSafeEqual`, в JSON-результатах init токены не возвращаются (новый путь `initializeTeam`), token-файлы не копируются в plugin source (подтверждено в `plugin-renderer.ts`).
- **Валидация ввода:** strict zod-схемы на всех HTTP-маршрутах и MCP-инструментах, payload ≤ 32 KiB, HTTP body ≤ 64 KiB, UUID-проверки, `agentId` regex.
- **Доставка fail-closed:** claim привязан к (sessionId, generation), `DELIVERY_UNCERTAIN` без клиентской идемпотентности → карантин + pause участника (не слепой replay), acceptance-проба одноразовая.
- **SQLite:** WAL, `BEGIN IMMEDIATE`, транзакции с rollback, CHECK-констрейнты состояний, UNIQUE по `(project, sender, idempotency_key)`.
- **Плагин:** ownership-файл предотвращает перезапись чужого plugin source; версия манифеста детерминированно зависит от состава ролей.

## 3. Находки

### HIGH

**H1. Probe доверяет порту: токен отправляется непроверенному слушателю.**
`ensureRelay()` / supervisor при старте шлёт `listParticipants` **с Bearer-токеном** на всё, что слушает 127.0.0.1:4100, и лишь по ответу проверяет совместимость проекта. Локальный процесс (в т.ч. другого пользователя), занявший порт до первого старта relay, получает валидный токен роли при каждом probe/reconnect-цикле. Проверка проекта fail-closed защищает _целостность_ (relay не поднимется поверх чужого), но _конфиденциальность токена_ уже нарушена. Далее атакующий освобождает порт и impersonирует роль на настоящем relay.
_Рекомендация:_ ввести неаутентифицированный `/v1/health` (project key/hash, protocol version, без участников) и слать токен только после его валидации; в перспективе — взаимная аутентификация (relay-токен, известный только ролям). До реализации — зафиксировать риск в README: на многопользовательских машинах порт 4100 считается недоверенным до проверки.

**H2. MCP-конфиг не требует loopback для `relayUrl`.**
Adapter-конфиги валидируют `relayUrl` через `loopbackHttp` (`src/config/adapter.ts`), а `configurationSchema` в `src/mcp/stdio.ts` — только `z.string().url()`. Подменённый или ошибочный MCP-конфиг направит токен Bearer-заголовком на произвольный URL (в т.ч. внешний http — токен уйдёт открытым текстом). Сгенерированные конфиги безопасны (пишутся самим init), но legacy-конфиги ручные, и именно они описаны в README §3.
_Рекомендация:_ применить тот же `loopbackHttp` refine в `src/mcp/stdio.ts`.

### MEDIUM

**M1. Токены append-only: нет отзыва, ротации, экспирации.**
`CredentialStore.issue()` только добавляет хэши; все когда-либо выпущенные токены валидны бессрочно. Прямое следствие для сегодняшнего инцидента с перевыпуском: после `ensureCredential`-перевыпуска **старый токен продолжает работать** — если инцидент был вызван подозрением на утечку, перевыпуск ничего не изолировал. Инструментов (`revoke`, `rotate`, список активных токенов) нет; `doctor` валидность токенов не проверяет.
_Рекомендация:_ команда `synloq rotate-token --agent-id <id>` (новый токен + удаление старых хэшей роли) и runbook в docs: «при подозрении на утечку — rotate, а не reissue».

**M2. Нет ограничения конкурентных соединений / long-poll.**
Аутентифицированная роль может открыть неограниченное число параллельных `waitMs=25000` запросов: каждый держит соединение, таймер и слушателя в `EventEmitter` (`setMaxListeners(0)`). Исчерпание fd/памяти relay останавливает координацию всего проекта. Rate limit покрывает только send-путь.
_Рекомендация:_ per-identity лимит одновременных запросов (например, 2 long-poll + N обычных), отказ с `RATE_LIMITED`.

**M3. Бесконечный рост БД: нет retention/GC.**
Rate limits ограничивают приток (~14k сообщений/сутки/отправитель), но хранение неограничено: acked-сообщения не удаляются, dedup-записи вечны (UNIQUE-констрейнт — фактически бесконечное окно; spec §5 честно фиксирует расхождение как «safer-than-spec», но цена — рост). Pending-лимит (100/1 MiB) защищает только очередь, не архив.
_Рекомендация:_ фоновый GC acked-сообщений старше N дней (N по умолчанию 30) с сохранением dedup-ключей отдельно от тел.

**M4. Нет аудита.**
Auth-неудачи, operator pause/resume/replace-session, выпуск/перевыпуск токенов нигде не фиксируются. Сегодняшний инцидент с токенами пришлось разбирать по косвенным признакам. Для coordination-инструмента с несколькими автономными агентами минимальный append-only audit (кто/когда/действие/message id, без тел) — дешёвый и высокоценный.
_Рекомендация:_ таблица `audit_log` в SQLite + вывод в `doctor`.

### LOW

- **L1.** `initCommand` (`src/cli/commands.ts:62`) — неиспользуемый CLI-экспорт, возвращающий plaintext-токены в JSON. Риск утечки в логи при случайном подключении. Удалить или явно пометить deprecated/internal.
- **L2.** `issue()`/`ensureCredential()` — read-modify-write `credentials.json` без блокировки; конкурентные init теряют записи (last-write-wins через atomic rename). Маловероятно (init ручной), но дёшево лечится lock-файлом.
- **L3.** `writeTextAtomic` без fsync перед rename — окно потери файла при краше ОС; на Windows `rename` поверх открытого файла может падать. Для токенов/состояния приемлемо, для credentials.json после rotate — стоит fsync.
- **L4.** Файлы пишутся с 0600, но каталоги `~/.synloq/*` создаются с umask-умолчанием; на Windows POSIX-режимы фактически игнорируются. Для single-user машины приемлемо — задокументировать, не чинить.
- **L5.** Расхождения spec ↔ impl (часть уже отмечена в protocol v1 как gaps; добавляю найденное):
  - hop limit: spec фиксирует **4**, а `roleInstructions` в `plugin-renderer.ts` говорит агентам «eight Synloq hops» — агенты будут считать по-разному; привести к одному числу.
  - protocol §6 предписывает эскалацию «NOTICE оператору», но `operator` не participant → `requireParticipant` отклонит такое сообщение как `UNKNOWN_RECIPIENT`. Канал эскалации сейчас нереализуем через relay.
  - strict zod-схемы HTTP API конфликтуют с protocol §1 «unknown fields MUST be ignored» — любое добавление поля в v1.1 сломает старые relay. Нужно решение о forward-compat до заморозки v1.
  - **Асимметрия участников (наблюдено вживую 2026-11-12):** `requireParticipant` проверяет только `to`, не `from`. После добавления роли `dev` в `synloq.yaml` без рестарта relay роль `dev` смогла отправить сообщение (её токен валиден, получатель — participant), а ответ в тред отклонён с `UNKNOWN_RECIPIENT`, потому что `dev` отсутствует в загруженном при старте списке участников. Следствия: (а) манифест читается один раз при старте relay — добавление ролей требует рестарта, иначе рождаются «односторонние» роли; (б) стоит либо требовать participant-статус и для `from` (сообщение dev тогда вообще не принялось бы), либо принимать reply на любой существующий threadId независимо от манифеста. Минимум — документировать, что изменение `synloq.yaml` применяется только рестартом relay.

## 4. Атомарность состояния

- **SQLite-слой корректен:** транзакции `BEGIN IMMEDIATE`, claim через один `UPDATE ... WHERE delivery_state='stored'` (двойной claim невозможен даже при гипотетических двух writer'ах), генерации сессий отсекают stale-binding.
- **Единственность writer'а — дисциплина, не механизм.** README требует «ровно один writer», но технически второй `synloq serve` на другом порту той же БД не запрещён. SQLite WAL сериализует запись (целостность не пострадает), но разойдутся in-memory rate-limit buckets и dispatcher'ы. Рекомендация: lock-файл рядом с БД (advisory lock), отказ второго serve с понятной ошибкой.
- **JSON-файлы состояния** (credentials, team-state, mcp-конфиги) атомарны через temp+rename; слабые места — L2 (нет lock на read-modify-write) и L3 (нет fsync).
- **TeamState:** strict-схема + сверка ключа записи с `agentId` — подмена связки роль↔чат через ручную правку файла обнаруживается.

## 5. Поверхности абьюза

- **Idempotency keys:** sender-controlled, 1–128 символов, конфликт контента отклоняется — корректно. Ключ не авторизуемый ресурс: украденный токен и так даёт все права роли. Риск «занять чужой ключ» отсутствует, т.к. dedup scoped по `(project, sender)`. Замечание по spec: бесконечное окно (см. M3) сегодня строже спеки — это безопасно, но при введении 7-дневного TTL нужно синхронно ввести GC тел сообщений, иначе окно TTL станет фикцией.
- **Лимиты (`protection.ts`):** покрывают send-путь (10/мин отправитель, 20/мин получатель, 100/1 MiB pending, 12 сообщений/2 мин → auto-pause треда). Не покрывают: inbox/wait/ack/list (см. M2) и сессионные эндпоинты (heartbeat/register — можно дёшево шуметь heartbeat'ами; влияние ограничено, т.к. heartbeat одной роли идемпотентен). In-memory buckets сбрасываются при рестарте/ре-элекшне relay — временное окно усиленного флуда после recovery; приемлемо для local-first, зафиксировать как известное.
- **Ack semantics:** идемпотентен, только получатель, fast-forward состояний задокументирован в spec §3 как convenience — корректно. Ack не доказывает прочтение человеком/моделью — семантика «read/taken into processing» выдержана в документации; completion только через RESULT/BLOCKED. Здесь всё чисто.
- **Dispatcher:** backoff до 30 с, карантин при uncertain-без-идемпотентности — fail-closed. Адаптер, системно возвращающий `DELIVERY_UNCERTAIN`, self-DoS'ит своего участника (pause) — это осознанный безопасный выбор, требует operator resume.

## 6. Позиция для общего ревью: простота и обновляемость

**Что ломается при апгрейде сегодня:**

1. **Абсолютные пути в артефактах.** Сгенерированные MCP-конфиги и `kimi.plugin.json` содержат абсолютные пути к `dist/`, synloqHome, projectRoot. Перенос репозитория или synloqHome = полная перегенерация + Install/Update. Это главный источник «у пользователя всё сломалось после обновления». Рекомендация: команда `synloq doctor --repair` (перегенерация конфигов по сохранённому team-state) как документированный путь починки.
2. **Даунгрейд невозможен после миграции БД.** `openDatabase` принимает `user_version` 0–4 и выставляет 4; старый бинарь откажется открывать новую БД. Fail-closed — правильно, но должно быть явно сказано в release notes: «обновление необратимо для БД».
3. **Перевыпуск токенов (сегодняшний кейс).** Цепочка хрупких мест: reuse работает только если token-файл и `credentials.json` согласованы и synloqHome не переехал; при потере `credentials.json` все роли молча получают новые токены, уже запущенные MCP-процессы держат старые в памяти и начинают получать 401 без диагностики «токен отозван/неизвестен». Рекомендации: (а) rotate-команда из M1; (б) различимый ответ при unknown token vs malformed (сейчас оба — generic UNAUTHORIZED; для диагностики достаточно кода ошибки, без раскрытия деталей); (в) runbook «что делать при 401 после init».
4. **Protocol v1 внедрение.** Полей `version/type/hops/reasonCode` нет в схеме и БД; strict-валидация (L5) означает, что rolling upgrade relay↔клиенты невозможен — нужна либо leniency к неизвестным полям, либо явный version gate на `/v1/`. Решить до публикации v1 как стабильной.

**Простота для массового пользователя — оценка положительная:** шесть инструментов, автоматический relay, отсутствие agent-facing управления credentials — правильный минимум. Главная угроза простоте — не security-фичи, а обновляемость: сегодня «починка» = разбираться с тремя хранилищами (synloq.yaml, team-state, credentials) вручную. Инвестиция в `doctor --repair` и rotate-команду даст больше для массового пользователя, чем любая криптография.
