# Security review — 2026-11-12

- **Reviewer:** Security role
- **Scope:** branch `feat/synloq-mvp`, HEAD `c69c726`
- **Method:** static analysis of code and documentation (README.md, docs/protocol/v1.md, src/relay/, src/config/, src/storage/, src/init/, src/mcp/, src/transport/, plugins/synloq/). No code was changed and no tests were run — this is an analytical review, not a build verification.
- **Context:** first review after the role's onboarding; occasion — the planned MVP check and today's token re-issue incident.

---

## 1. Threat model

**Assets:** role and operator bearer tokens (`<synloqHome>/credentials/`), message content in SQLite, delivery-state integrity, relay availability.

**Trust boundary:** loopback HTTP `127.0.0.1:4100` without TLS. This is the correct choice for local-first, but it is important to pin down exactly what it means:

1. **Any local process** (of any user on the machine) can open a TCP connection to the relay. Without a valid token it gets a 401 — brute-forcing 256-bit tokens is impractical; there is no limit on authentication attempts (not critical at this entropy).
2. **Anyone on the machine can occupy port 4100 before the relay** (an unprivileged port). This is the main practical threat — see H1.
3. **A process running as the current user** can read token files directly (0600 does not protect against the user themselves) and rewrite `credentials.json`, adding its own hash. This is a fundamental property of local-first, not a defect, but it must be stated explicitly in the threat model: compromising any of the user's processes = compromising all project roles.
4. **Participant agents are trusted but not omnipotent:** a role with a valid token can message any participant, read only its own inbox, ack only its own messages. The operator token = full control (pause/resume/replace-session/doctor/send as `operator`). Theft of the operator token is the worst project-level scenario.

**Out of scope (explicitly, matching README/protocol §9):** external network attacks (loopback-only), traffic encryption, untrusted operators, prompt injection between agents (the relay is a transport, not a content filter).

## 2. What is already done right (confirmed in code)

- **Triple loopback-only guarantee:** `RelayHttpServer.listen()` rejects non-loopback hosts; the supervisor `endpoint()` accepts only `http://127.0.0.1` / `http://[::1]` without userinfo/query/path; adapter configs are validated by the `loopbackHttp` refine. Fail-closed in all three places.
- **No sender spoofing:** `from` is set from the authenticated identity (`relay-service.ts:49`); client input for `from`/`project` is discarded by the schema.
- **Recipient authorization:** inbox, ack, reply-parent, delivery receipt/failure — everywhere checks `to === identity.agentId`; another role's inbox is inaccessible (except operator — deliberate).
- **Tokens:** 32 bytes of `randomBytes`, SHA-256 at rest, `timingSafeEqual` comparison, init JSON results do not return tokens (the new `initializeTeam` path), token files are never copied into the plugin source (confirmed in `plugin-renderer.ts`).
- **Input validation:** strict zod schemas on all HTTP routes and MCP tools, payload ≤ 32 KiB, HTTP body ≤ 64 KiB, UUID checks, `agentId` regex.
- **Fail-closed delivery:** claims are bound to (sessionId, generation); `DELIVERY_UNCERTAIN` without client idempotency → quarantine + participant pause (not a blind replay); the acceptance probe is single-use.
- **SQLite:** WAL, `BEGIN IMMEDIATE`, transactions with rollback, CHECK constraints on states, UNIQUE on `(project, sender, idempotency_key)`.
- **Plugin:** the ownership file prevents overwriting someone else's plugin source; the manifest version deterministically depends on the role set.

## 3. Findings

### HIGH

**H1. The probe trusts the port: the token is sent to an unverified listener.**
`ensureRelay()` / the supervisor at startup sends `listParticipants` **with the Bearer token** to whatever listens on 127.0.0.1:4100, and only checks project compatibility from the response. A local process (including another user's) that occupied the port before the first relay start receives a valid role token on every probe/reconnect cycle. The fail-closed project check protects _integrity_ (the relay will not start on top of a foreign one), but _token confidentiality_ is already violated. The attacker then releases the port and impersonates the role on the real relay.
_Recommendation:_ introduce an unauthenticated `/v1/health` (project key/hash, protocol version, no participants) and send the token only after validating it; longer term — mutual authentication (a relay token known only to roles). Until implemented — record the risk in the README: on multi-user machines port 4100 is considered untrusted until verified.

**H2. The MCP config does not require loopback for `relayUrl`.**
Adapter configs validate `relayUrl` via `loopbackHttp` (`src/config/adapter.ts`), while `configurationSchema` in `src/mcp/stdio.ts` uses only `z.string().url()`. A substituted or erroneous MCP config would send the token in a Bearer header to an arbitrary URL (including external http — the token would go in plaintext). Generated configs are safe (written by init itself), but legacy configs are manual, and those are exactly what README §3 describes.
_Recommendation:_ apply the same `loopbackHttp` refine in `src/mcp/stdio.ts`.

### MEDIUM

**M1. Tokens are append-only: no revocation, rotation, or expiry.**
`CredentialStore.issue()` only appends hashes; every token ever issued remains valid indefinitely. A direct consequence for today's re-issue incident: after an `ensureCredential` re-issue **the old token keeps working** — if the incident was caused by a suspected leak, the re-issue isolated nothing. There are no tools (`revoke`, `rotate`, list of active tokens); `doctor` does not check token validity.
_Recommendation:_ a `synloq rotate-token --agent-id <id>` command (new token + removal of the role's old hashes) and a runbook in docs: "on suspected leak — rotate, not reissue".

**M2. No limit on concurrent connections / long polls.**
An authenticated role can open an unlimited number of parallel `waitMs=25000` requests: each holds a connection, a timer, and a listener in the `EventEmitter` (`setMaxListeners(0)`). Exhausting the relay's fds/memory stops coordination for the whole project. The rate limit covers only the send path.
_Recommendation:_ a per-identity limit on concurrent requests (e.g. 2 long polls + N regular), rejected with `RATE_LIMITED`.

**M3. Unbounded DB growth: no retention/GC.**
Rate limits bound the inflow (~14k messages/day/sender), but storage is unbounded: acked messages are never deleted, dedup records are eternal (the UNIQUE constraint — effectively an infinite window; spec §5 honestly records the divergence as "safer-than-spec", but the price is growth). The pending limit (100/1 MiB) protects only the queue, not the archive.
_Recommendation:_ background GC of acked messages older than N days (default N = 30), keeping dedup keys separately from bodies.

**M4. No audit.**
Auth failures, operator pause/resume/replace-session, token issue/re-issue are nowhere recorded. Today's token incident had to be investigated from indirect evidence. For a coordination tool with several autonomous agents, a minimal append-only audit (who/when/action/message id, without bodies) is cheap and highly valuable.
_Recommendation:_ an `audit_log` table in SQLite + output in `doctor`.

### LOW

- **L1.** `initCommand` (`src/cli/commands.ts:62`) — an unused CLI export returning plaintext tokens in JSON. Risk of leakage into logs if accidentally wired up. Remove or explicitly mark deprecated/internal.
- **L2.** `issue()`/`ensureCredential()` — read-modify-write of `credentials.json` without locking; concurrent inits lose entries (last-write-wins via atomic rename). Unlikely (init is manual), but cheaply fixed with a lock file.
- **L3.** `writeTextAtomic` without fsync before rename — a file-loss window on OS crash; on Windows `rename` over an open file can fail. Acceptable for tokens/state; for `credentials.json` after rotate, fsync is worthwhile.
- **L4.** Files are written with 0600, but `~/.synloq/*` directories are created with the umask default; on Windows POSIX modes are effectively ignored. Acceptable for a single-user machine — document, don't fix.
- **L5.** Spec ↔ impl divergences (some already noted in protocol v1 as gaps; adding what I found):
  - hop limit: the spec fixes **4**, while `roleInstructions` in `plugin-renderer.ts` tells agents "eight Synloq hops" — agents will count differently; align to one number.
  - protocol §6 prescribes escalation via "NOTICE to the operator", but `operator` is not a participant → `requireParticipant` rejects such a message as `UNKNOWN_RECIPIENT`. The escalation channel is currently not implementable through the relay.
  - strict zod schemas of the HTTP API conflict with protocol §1 "unknown fields MUST be ignored" — any field addition in v1.1 will break old relays. A forward-compat decision is needed before freezing v1.
  - **Participant asymmetry (observed live on 2026-11-12):** `requireParticipant` checks only `to`, not `from`. After the `dev` role was added to `synloq.yaml` without a relay restart, the `dev` role could send a message (its token is valid, the recipient is a participant), while the reply in the thread was rejected with `UNKNOWN_RECIPIENT` because `dev` is absent from the participant list loaded at startup. Consequences: (a) the manifest is read once at relay startup — adding roles requires a restart, otherwise "one-way" roles are born; (b) either require participant status for `from` as well (dev's message would then not be accepted at all), or accept replies to any existing threadId regardless of the manifest. At minimum — document that `synloq.yaml` changes take effect only on relay restart.

## 4. State atomicity

- **The SQLite layer is correct:** `BEGIN IMMEDIATE` transactions, claim via a single `UPDATE ... WHERE delivery_state='stored'` (a double claim is impossible even with two hypothetical writers), session generations cut off stale bindings.
- **Single writer is a discipline, not a mechanism.** The README requires "exactly one writer", but technically a second `synloq serve` on a different port of the same DB is not forbidden. SQLite WAL serializes writes (integrity is preserved), but in-memory rate-limit buckets and dispatchers would diverge. Recommendation: a lock file next to the DB (advisory lock), with the second serve failing with a clear error.
- **JSON state files** (credentials, team-state, MCP configs) are atomic via temp+rename; weak points are L2 (no lock on read-modify-write) and L3 (no fsync).
- **TeamState:** strict schema + cross-check of the record key against `agentId` — tampering with the role↔chat binding via manual file editing is detected.

## 5. Abuse surfaces

- **Idempotency keys:** sender-controlled, 1–128 chars, content conflict rejected — correct. The key is not an authorized resource: a stolen token already grants all role rights. There is no risk of "occupying someone else's key" since dedup is scoped by `(project, sender)`. A note on the spec: the infinite window (see M3) is stricter than the spec today — that is safe, but when the 7-day TTL is introduced, GC of message bodies must be introduced in sync, otherwise the TTL window becomes a fiction.
- **Limits (`protection.ts`):** cover the send path (10/min sender, 20/min recipient, 100/1 MiB pending, 12 messages/2 min → thread auto-pause). Not covered: inbox/wait/ack/list (see M2) and session endpoints (heartbeat/register — one can cheaply spam heartbeats; impact is limited because one role's heartbeat is idempotent). In-memory buckets reset on relay restart/re-election — a temporary window of amplified flooding after recovery; acceptable for local-first, record as known.
- **Ack semantics:** idempotent, recipient-only, state fast-forward documented in spec §3 as a convenience — correct. Ack does not prove reading by a human/model — the "read/taken into processing" semantics is maintained in the documentation; completion only via RESULT/BLOCKED. All clean here.
- **Dispatcher:** backoff up to 30 s, quarantine on uncertain-without-idempotency — fail-closed. An adapter that systematically returns `DELIVERY_UNCERTAIN` self-DoSes its participant (pause) — this is a deliberate safe choice requiring an operator resume.

## 6. Position for the joint review: simplicity and upgradability

**What breaks on upgrade today:**

1. **Absolute paths in artifacts.** Generated MCP configs and `kimi.plugin.json` contain absolute paths to `dist/`, synloqHome, projectRoot. Moving the repository or synloqHome = full regeneration + Install/Update. This is the main source of "everything broke after the update" for users. Recommendation: a `synloq doctor --repair` command (regenerating configs from the saved team-state) as the documented repair path.
2. **Downgrade is impossible after a DB migration.** `openDatabase` accepts `user_version` 0–4 and sets 4; an old binary will refuse to open the new DB. Fail-closed — correct, but release notes must state it explicitly: "the upgrade is irreversible for the DB".
3. **Token re-issue (today's case).** A chain of fragile spots: reuse works only if the token file and `credentials.json` are consistent and synloqHome has not moved; if `credentials.json` is lost, all roles silently receive new tokens, already-running MCP processes hold old ones in memory and start getting 401s with no "token revoked/unknown" diagnostics. Recommendations: (a) the rotate command from M1; (b) a distinguishable answer for unknown token vs malformed (currently both are generic UNAUTHORIZED; an error code suffices for diagnostics, without revealing details); (c) a runbook "what to do on 401 after init".
4. **Protocol v1 adoption.** The `version/type/hops/reasonCode` fields are absent from the schema and the DB; strict validation (L5) means a rolling upgrade of relay↔clients is impossible — either leniency towards unknown fields or an explicit version gate on `/v1/` is needed. Decide before publishing v1 as stable.

**Simplicity for the mass user — positive assessment:** six tools, automatic relay, no agent-facing credential management — the right minimum. The main threat to simplicity is not security features but upgradability: today "repair" means manually dealing with three stores (synloq.yaml, team-state, credentials). Investing in `doctor --repair` and the rotate command will do more for the mass user than any cryptography.
