# Synloq Protocol v1

Status: Accepted (CTO + Architect, 2026-11-12)
Version: envelope `"1"`
Date: 2026-11-11; errata 2026-11-12 (M1 spec↔impl reconciliation: strict-envelope/tolerant-payload policy, operator implicit participant §2.3, compatibility policy §9)
Owners: CTO (`cto`), Architect (`arch`)

Synloq is a local-first message relay between visible coding-agent chats. A loopback
HTTP relay persists state in SQLite; each role (agent) interacts through exactly six
MCP tools (`synloq_send`, `synloq_reply`, `synloq_inbox`, `synloq_ack`, `synloq_list`,
`synloq_wait`). This document specifies the application-level message protocol between
agents ("participants") and the relay.

Delivery is **inbox-on-request**: the relay stores messages and exposes them via
`inbox`/`wait`; there is no push channel into an active chat as part of this protocol.

---

## 1. Envelope

Every message is a JSON envelope:

| Field            | Type                   | Req   | Description                                                                  |
| ---------------- | ---------------------- | ----- | ---------------------------------------------------------------------------- |
| `version`        | string                 | yes   | Envelope version. MUST be `"1"` for v1.                                      |
| `type`           | string                 | yes   | Message type, see §2.                                                        |
| `id`             | string (UUID)          | yes   | Message identifier, assigned by the relay.                                   |
| `project`        | string                 | yes   | Project scope; messages never cross projects.                                |
| `threadId`       | string (UUID)          | yes   | Thread identifier. Inherited from the parent on reply; a new UUID otherwise. |
| `inReplyTo`      | string (UUID)          | no    | ID of the parent message; required for `RESULT`/`BLOCKED` responses.         |
| `from`           | string (agent id)      | yes   | Sender participant id (`^[a-z][a-z0-9-]{0,63}$`).                            |
| `to`             | string (agent id)      | yes   | Recipient participant id.                                                    |
| `hops`           | integer                | yes   | Hop counter, see §4. Sender sets `0`.                                        |
| `expectsReply`   | boolean                | yes   | Whether the sender awaits a `RESULT`/`BLOCKED` response in this thread.      |
| `idempotencyKey` | string                 | yes   | Sender-chosen key, 1–128 chars, unique per sender, see §5.                   |
| `reasonCode`     | string                 | cond. | Required iff `type = "BLOCKED"`, see §7.                                     |
| `createdAt`      | string (ISO 8601, UTC) | yes   | Relay timestamp of acceptance.                                               |
| `payload`        | string                 | yes   | Message body, 1 byte – 32 KiB (UTF-8).                                       |

The envelope is **strict**: a receiver MUST reject an envelope carrying unknown
top-level fields with `BLOCKED(invalid_input)` (§7). Forward compatibility of the
envelope is achieved exclusively through version negotiation (§1.1), never through
field tolerance — a silently ignored envelope field can change routing or contract
semantics without any party noticing.
The payload is **tolerant**: when payload schemas become structured (post-v1), a
receiver MUST ignore unknown payload fields within a known `version`. Payload
extensions are minor changes under the compatibility policy (§9).

### 1.1 Version negotiation

A receiver (relay or agent) that reads an envelope with an unknown `version` MUST NOT
silently drop it. The receiver rejects it with a `BLOCKED` message carrying
reason code `unsupported_version` (§7), addressed to the original sender, in the same
thread (or a new thread if the incoming envelope has no parseable `threadId`).
A receiver MUST NOT attempt to interpret any field of an unknown-version envelope
beyond `version`, `from`, `to`, `threadId`, and `idempotencyKey`.

> Implementation gap: the current relay model (`src/domain/message.ts`) has no
> `version`, `type`, `hops`, or `reasonCode` fields. v1 adoption requires adding them
> to the schema and to `sendMessageInputSchema` with `.strict()` validation.

## 2. Message types

### 2.1 Conversational types

| Type      | `expectsReply`   | ack      | Semantics                                                                               |
| --------- | ---------------- | -------- | --------------------------------------------------------------------------------------- |
| `QUERY`   | typically `true` | required | Information request; no state change expected from the receiver.                        |
| `TASK`    | `true`           | required | Work order. The receiver commits to producing `RESULT` or `BLOCKED` in the same thread. |
| `RESULT`  | MUST be `false`  | required | Successful outcome of a `TASK`/`QUERY`. Terminal for the request.                       |
| `BLOCKED` | MUST be `false`  | required | Failure/rejection of a request. MUST carry `reasonCode` (§7). Terminal for the request. |
| `NOTICE`  | MUST be `false`  | optional | One-way information. The only type without a mandatory ack.                             |

Rationale for `expectsReply=false` on `RESULT`/`BLOCKED`: otherwise confirmations
recurse (`RESULT` on a `RESULT` on a …) and threads never terminate.

`NOTICE` still MUST be stored by the relay like any other message: inbox-on-request is
the only guaranteed channel, and an un-acked `NOTICE` remains visible in the inbox.

### 2.2 Service types

Service messages are generated by the **relay**, never by participants. They use
`from = "relay"` (reserved agent id, not assignable to a participant) and
`expectsReply = false`.

| Type                | Semantics                                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BLOCKED` (service) | Protocol-level rejection produced by the relay: `unsupported_version`, `hop_limit_exceeded`, `unknown_recipient`, `invalid_input`, `idempotency_conflict`. |
| `NOTICE` (service)  | Operator-facing escalations, e.g. response timeout (§6), quarantine events.                                                                                |

Participants MUST NOT send service messages; the relay rejects such attempts with
`invalid_input`. A service `BLOCKED` counts as a terminal `BLOCKED` for the request it
references (via `inReplyTo`).

### 2.3 The operator (implicit participant)

The project operator is an **implicit participant** with the reserved agent id
`"operator"`. The operator is not listed in the project manifest and exists in every
project by definition. Rules:

- Participants MAY address the operator with `NOTICE` **only**. Any other message type
  addressed to `"operator"` is rejected by the relay with `invalid_input`.
- The operator never sends protocol messages in v1 (the operator channel is
  read-only); see §6 for the escalation flow.
- `unknown_recipient` MUST NOT be raised for `"operator"`; the relay treats the id as
  always valid for `NOTICE`.

This makes the §6 escalation path implementable without expanding the manifest-based
participant registry.

## 3. Ack semantics

Delivery states: `stored → submitted → delivered → acked` (already implemented in
`src/storage/message-store.ts`, `transition()`).

- **delivered ≠ read.** `delivered` records transport to the visible chat only.
- **ack = read.** Calling `synloq_ack` asserts only "read / taken into processing".
  It never asserts completion.
- **Completion is signalled exclusively** by a `RESULT` or `BLOCKED` message in the
  same thread.
- **ack is idempotent.** Acknowledging an already-acked message returns success and
  changes nothing (matches `acknowledge()` in `message-store.ts`).
- Ack of a message whose delivery state is behind `delivered` fast-forwards the state
  machine (`stored → submitted → delivered → acked`); this is an implementation
  convenience and MUST NOT be relied upon semantically.
- Ack is mandatory for `QUERY`, `TASK`, `RESULT`, `BLOCKED`; optional for `NOTICE`.

## 4. Hop limit

`hops` guards against routing loops. v1 fixes the limit at **exactly 4** (no range;
the 4–8 discussion space is deferred to v2).

Semantics (incremental, not decremental):

1. The sender creates the envelope with `hops = 0`.
2. Each relay hop that forwards the message to the next leg increments `hops` by 1
   _before_ forwarding. Direct point-to-point delivery on the local relay is the
   first and normally only hop (`hops = 1` on the stored record... see note below).
3. When a relay receives a message with `hops = 4` that requires a **further** hop,
   it MUST NOT forward it. The relay drops the message from the forwarding queue and
   returns a service `BLOCKED` to the original sender with
   `reasonCode = "hop_limit_exceeded"`. There is no automatic retry: re-sending with
   a fresh `idempotencyKey` would traverse the same loop.
4. A message with `hops = 4` that has **reached its final recipient** is delivered
   normally — the limit bounds forwards, not arrivals.

Loop example: A → R1 → R2 → R3 → R4 → R1 … The message leaves A with `hops=0`; it is
forwarded by R1 (`1`), R2 (`2`), R3 (`3`), R4 (`4`). R4's forwarding decision would
require hop 5; R4 therefore drops the message and issues
`BLOCKED(hop_limit_exceeded)` to A. Without the counter, A's message would circulate
indefinitely and saturate the rate limits (§8) without an actionable error.

> Implementation gap: the current relay is single-hop (sender → local relay →
> recipient) and has no `hops` field. For v1 on a single relay the counter is
> invariant at 1, but the field and the drop rule are specified now so multi-relay
> federation in v2 does not change the envelope.

## 5. Idempotency and deduplication

- `idempotencyKey` is REQUIRED, 1–128 characters, and MUST be unique per sender.
  Recommended format: `<purpose>-<yyyyMMdd>-<seq>` or a UUID.
- Deduplication key: **`(sender, idempotencyKey)`** (scoped per project).
- **Window: 7 days.** Within 7 days of first acceptance, a retry with the same key:
  - with **identical content** (`to`, `payload`, `expectsReply`, `inReplyTo`) returns
    the original stored message and creates no new one;
  - with **different content** is rejected with `IDEMPOTENCY_CONFLICT` (relay) —
    surfaced to the peer as `BLOCKED(idempotency_conflict)` if it arrives across
    relay boundaries.
- Delivery is **at-least-once**. The receiver MUST deduplicate on
  `(from, idempotencyKey)` (falling back to `id` for legacy envelopes) before acting.
- After the 7-day window the relay MAY garbage-collect dedup records; a late retry
  with the same key is then accepted as a new message. Senders that must not duplicate
  side effects across the window boundary MUST choose fresh keys per logical request.
- A retry after the response timeout (§6) MUST reuse the same `idempotencyKey`.

> Implementation gap: current dedup in `SQLiteMessageStore.create()` matches on
> `(project, sender, idempotencyKey)` with **no expiry** — effectively an infinite
> window. v1 adds the 7-day TTL; until implemented, the safer-than-spec behavior is
> noted as a deliberate divergence (stricter dedup, never weaker).

## 6. Failure handling and timeouts

- **Response timeout: 30 minutes.** When a sender issues a message with
  `expectsReply = true` and no `RESULT`/`BLOCKED` arrives in the thread within
  30 minutes of the last activity, the request is considered timed out.
  - Timeout is enforced **agent-side**, not by the relay: the relay keeps the message;
    the sending agent escalates.
  - On timeout the sender MAY retry the request once with the **same**
    `idempotencyKey` (no new message is created by dedup).
  - Escalation = `NOTICE` to the operator (§2.3). There is **no
    automatic retry loop**; the decision belongs to the operator.
- Transport-level failures (relay unreachable, storage failure) surface as the
  error codes of §7 through the MCP tool result (`isError: true`) and are not
  protocol messages.
- `DELIVERY_UNCERTAIN` quarantine behavior (pause of the recipient's delivery gate)
  is relay-internal and unchanged by this specification.

## 7. BLOCKED reason codes

Every `BLOCKED` message MUST carry a machine-readable `reasonCode` (lower snake case)
and a human-readable explanation in `payload`. Codes are open for extension in minor
revisions; v1 defines:

| Code                   | Producer    | Meaning                                                     |
| ---------------------- | ----------- | ----------------------------------------------------------- |
| `unsupported_version`  | relay       | Envelope `version` not supported (§1.1).                    |
| `hop_limit_exceeded`   | relay       | Message needed a 5th hop (§4). No retry.                    |
| `unknown_recipient`    | relay       | `to` is not a participant of the project.                   |
| `invalid_input`        | relay       | Schema violation, forbidden service type, oversize payload. |
| `idempotency_conflict` | relay       | Key reused with different content (§5).                     |
| `rate_limited`         | relay       | Sender/recipient rate limit exceeded (§8).                  |
| `queue_full`           | relay       | Recipient pending-queue limits exceeded.                    |
| `paused`               | relay       | Project/participant/thread pause gate is active.            |
| `timeout`              | agent       | No response within 30 minutes (§6).                         |
| `rejected`             | agent       | Recipient declines the request; reason in `payload`.        |
| `unauthorized`         | relay/agent | Identity or authorization failure.                          |
| `delivery_uncertain`   | relay       | Outcome of a delivery attempt cannot be established.        |
| `not_found`            | relay       | Referenced `inReplyTo`/message does not exist.              |
| `storage_failure`      | relay       | Persistent storage error.                                   |
| `internal`             | any         | Unclassified failure; `payload` MUST describe it.           |

The relay's internal `SynloqError` codes (`src/domain/errors.ts`, UPPER_SNAKE) map
onto these protocol codes **only partially**, by lowercasing where applicable:

| `SynloqError` code      | Protocol reason code                                                            |
| ----------------------- | ------------------------------------------------------------------------------- |
| `INVALID_INPUT`         | `invalid_input`                                                                 |
| `UNKNOWN_RECIPIENT`     | `unknown_recipient`                                                             |
| `IDEMPOTENCY_CONFLICT`  | `idempotency_conflict`                                                          |
| `RATE_LIMITED`          | `rate_limited`                                                                  |
| `QUEUE_FULL`            | `queue_full`                                                                    |
| `PAUSED`                | `paused`                                                                        |
| `STORAGE_FAILURE`       | `storage_failure`                                                               |
| `UNAUTHORIZED`          | `unauthorized`                                                                  |
| `DELIVERY_UNCERTAIN`    | `delivery_uncertain`                                                            |
| `NOT_FOUND`             | `not_found`                                                                     |
| `DUPLICATE_SESSION`     | — (relay-internal, never surfaces as a protocol reason)                         |
| `INCOMPATIBLE_PROTOCOL` | — (relay-internal; protocol-level version rejection uses `unsupported_version`) |

The mapping is not symmetric in the other direction either: `unsupported_version`,
`hop_limit_exceeded`, `timeout`, `rejected`, and `internal` are protocol-level codes
with no `SynloqError` counterpart. The two layers are intentionally kept consistent
**where they overlap**, not one-to-one; conformance tests MUST assert the partial
mapping above rather than full synchronization.

## 8. Protection limits (informative)

Current defaults (`src/relay/protection.ts`), not part of the protocol contract but
referenced by `rate_limited`/`queue_full` and by the hop-limit rationale:

- sender: 10 messages/min; recipient: 20 messages/min
- pending queue per recipient: 100 messages / 1 MiB
- thread window: 12 messages per 2 minutes, then the thread is auto-paused
- payload: 32 KiB max

## 9. Versioning and compatibility policy

- **Minor change** (envelope `version` unchanged): editorial clarifications; new
  reason codes in §7 — a receiver that meets an unknown `reasonCode` MUST still treat
  the `BLOCKED` as terminal and SHOULD surface the raw code to the operator; new
  payload fields or payload conventions within a known version (payload is tolerant,
  §1). Minor changes are backward compatible: an un-upgraded v1 peer interoperates.
- **Major change** (`version` increments, e.g. `"2"`): adding, removing, or renaming
  envelope fields; new message types; changed semantics of existing fields; changed
  protocol constants (hop limit, dedup window, timeouts). Major changes interoperate
  only through version negotiation (§1.1); mixed-version behavior beyond rejection is
  unspecified.
- Deprecation: a feature marked deprecated in version N may be removed no earlier
  than the next major version.

---

## 10. Out of scope for v1

- Multi-relay federation (hop limit is already specified to accommodate it).
- Push delivery / streaming; `synloq_wait` polling (≤ 25 s) remains the wait primitive.
- Payload schemas per message type (task manifests, structured results) — v1 payload
  is opaque text; conventions like the `TASK:`/`RESULT` prefixes are informal.
- Encryption and non-loopback transport.
