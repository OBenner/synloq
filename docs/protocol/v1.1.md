# Protocol v1.1

Status: **accepted** (double approval per §9 on 2026-11-17: lead developer + CTO).
Base: protocol v1 + errata 2026-11-12.

## Change set 1. Sender MUST be a registered participant (issue #10)

New normative section §2.5 (after §2.4):

### §2.5 Sender registration (normative)

A message whose `from` is not a registered participant of the project MUST be
rejected by the relay at acceptance time. The participant registry is the same
registry that validates `to` (§1); the reserved ids `relay` and `operator`
(§2.2, §2.3) cannot appear as `from` on participant-originated messages.

Rejection is synchronous at the acceptance boundary — an error response to the
send call, not a stored `BLOCKED`. A message that cannot be replied to MUST NOT
be accepted at all.

The sender check happens BEFORE any dedup/idempotency effect and before any
write, including the replay path: an unregistered sender never receives a
replay response from another participant's ledger entry.

Rationale (incident 2026-11-12): a sender holding a valid credential but no
registry entry could post messages; every reply then failed with
`unknown_recipient`, leaving correspondents with undeliverable responses and
the sender with false confidence of delivery.

§7 addition (minor per §9 — new reason code):

| Code             | Producer | Meaning                                                                                          |
| ---------------- | -------- | ------------------------------------------------------------------------------------------------ |
| `unknown_sender` | relay    | `from` is not a participant of the project; the send is rejected at acceptance and never stored. |

SynloqError mapping addition:

| `SynloqError` code | Protocol reason code                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `UNKNOWN_SENDER`   | `unknown_sender` (HTTP error at the send boundary; never a stored delivery reason — mirrors `unknown_recipient` for sends) |

Backward compatibility (§9 minor): tightening at the acceptance side. A sender
without a registry entry could not receive replies already, so no working
workflow is broken; wire compatibility unaffected (un-upgraded v1 peers are
relay implementations, not envelope producers).

## Change set 2. Reserved agent ids (issue #5)

Status: **pending double approval** (per §9 governance; author: Architect,
2026-11-19; approval by lead developer and CTO is tracked in the PR).

New normative section §2.6 (after §2.5):

### §2.6 Reserved agent ids (normative)

The agent ids `relay` (§2.2) and `operator` (§2.3) are reserved. Reservation is
an exact, case-sensitive match of the lowercase identifier.

1. A project manifest MUST NOT declare a participant with a reserved id. A
   manifest that does is invalid: the relay MUST refuse to load it (fail-loud
   configuration error, not a protocol message).
2. A message whose `from` equals a reserved id MUST be rejected by the relay at
   the acceptance boundary with the reason code `sender_reserved` — an error
   response to the send call, never a stored message (same acceptance-time
   semantics as §2.5). This sharpens the generic `invalid_input` rejection that
   v1 §2.2 specifies for participant-sent service messages: the dedicated code
   lets an operator distinguish an attempt to speak as the relay from an
   ordinary schema violation.
3. Channel issuance MUST refuse to create credentials bound to a reserved id
   (`synloq init` and any future registration path). No credential may ever map
   a reserved id to a usable channel.

§7 addition (minor per §9 — new reason code):

| Code              | Producer | Meaning                                                                                                  |
| ----------------- | -------- | -------------------------------------------------------------------------------------------------------- |
| `sender_reserved` | relay    | `from` is a reserved agent id (`relay`/`operator`); the send is rejected at acceptance and never stored. |

SynloqError mapping addition:

| `SynloqError` code | Protocol reason code                                                        |
| ------------------ | --------------------------------------------------------------------------- |
| `SENDER_RESERVED`  | `sender_reserved` (HTTP error at the send boundary; never a stored BLOCKED) |

Backward compatibility (§9 minor): reserved ids could never deliver replies
already (no participant registry entry, no inbox), so no working workflow is
broken. A v1-conformant relay that still rejects with `invalid_input` remains
interoperable: receivers treat an unknown reason code as a terminal `BLOCKED`
(§9), and the acceptance-time rejection is identical.

## Non-goals

- Validation of the envelope sender against the registry is not caller
  authentication (the transport-auth-v2 contract is an orthogonal, separate
  namespace of errors).
- Registry membership semantics (who is added or removed, and when) are
  unchanged.
